# Status

**Phase:** 2, airports from X-Plane's own data. Phase 1 (BATC answered from X-Plane, ground to climb) and Phase 0 passed.

## Works
- Traffic, XPConnect side (not drawn in X-Plane yet): `serve` answers EnumerateSimObjectsAndLiveries from `mapping/liveries.json` (the 5,497 models MSFS listed), creates BATC's AI objects (AssignedObjectId), keeps their state from SetDataOnSimObject and events, answers BATC's ground-height polls (nearest served airport's elevation, else the ground under the user), and lists the traffic on the status page. Replay-tested against the recorded MSFS session (`TrafficTests`). Live on Ben's PC 2026-10-01 at YBBN: BATC created 45 aircraft and 3 tugs and its AI traffic talked on Ground. `--no-traffic` turns it off.
- Everyday use (0.3.0): `scripts/publish.ps1` builds a self-contained Windows zip (`XPConnect.exe`, the `FlightSimulator2024.exe` stub, `mapping/`, `README.txt`, two .cmd switches). Double-clicking `XPConnect.exe` offers to point BATC at it and then serves; `xpconnect batc on|off|status` adds or removes the two `SimConnect.cfg` redirects (BATC folder from its uninstall entry or `C:\BeyondATC`; an existing cfg is backed up and restored). Outside a source checkout, recordings go to `%LOCALAPPDATA%\XPConnect\recordings`. Package smoke-tested on Ben's PC 2026-10-01.
- Window (ADR-0006, not yet run on Ben's PC): double-clicking XPConnect.exe opens an FMS-style Avalonia window (STATUS, SETUP, SUPPORT, ABOUT; line select keys, keys 1-6 / Shift+1-6 / F1-F4, clicks on rows) that runs `serve` until closed. SETUP picks folders, connection mode, removes 0.3.0 cfg files, starts BeyondATC, opens the web page; SUPPORT toggles the session log, makes the support zip, shows the live log. The .cmd files are gone; `xpconnect start` keeps the console flow. Pages are tested from `CduPages.Build`; headless tests render every page (`XPCONNECT_SCREENSHOTS=<dir>` saves PNGs). Since the traffic work merged, STATUS shows how many aircraft the traffic add-on (the X-Plane plugin) is drawing and SETUP offers INSTALL>/UPDATE> for it (X-Plane must be closed), replacing the console start's install question.
- Automatic connection (ADR-0005): with `connection automatic` (the default), `serve` without `--listen` answers on MSFS's default pipe while the real MSFS is closed, plus `tcp:5112` for cfg-file set-ups. If MSFS starts, XPConnect closes its pipe clients and stops the stand-in, and resumes when MSFS closes. The status page says to close MSFS while it runs, and lists other MSFS add-ons as not used. `connection always-on` writes the cfg files and listens on TCP only. Pipe tested with BATC on Ben's PC on 2026-10-02 (both connections, gate, COM1); the MSFS step-aside is untested.
- Settings and support (not yet tried on Ben's PC): `xpconnect settings` saves the BeyondATC and X-Plane folders (used whenever `--batc` / `--xplane-root` are not given; a saved folder that no longer holds BATC or X-Plane falls back to automatic), session log on/off and days to keep, in `%LOCALAPPDATA%\XPConnect\settings.json`. `record`, `fake` and `serve` copy status lines (not packets) to `%LOCALAPPDATA%\XPConnect\logs\<time>-<mode>.log` and delete logs, LocalAppData recordings and support zips older than 7 days. `xpconnect support` (and "Create support file.cmd") zips the newest 5 logs, the newest recording (up to 300 MB), settings, BATC's Player.log and SimConnect.cfg files and the last 5 MB of X-Plane's Log.txt, with the profile path and Windows user name blanked out.
- Status page: `serve` shows http://localhost:5577/ (X-Plane connection, both BATC connections, airports sent and where from, a one-line "what to start next"); double-click start opens it in the browser. `--status-port`, `--no-status`. Not yet seen on Ben's PC.
- SimConnect packet framing, function and message names, and decoding of the common ATC-client calls (`src/XPConnect.Protocol`).
- `XPConnect record`: pass-through proxy that records a real client/sim session to JSONL and writes a call inventory.
- `XPConnect fake`: answers the Open handshake as MSFS 2020 or 2024 and serves the user aircraft's SimVars from a fixed snapshot (SF50 parked at YBBN, live clock, COM set events applied). `--facilities <recording.jsonl>` replays the airport data MSFS sent in a pass-through recording. Everything else is recorded and left unanswered.
- `src/XPConnect.SimStub` builds `FlightSimulator2024.exe`, the do-nothing process BATC needs to see before it connects. A console process with no window passes.
- `XPConnect serve` (first real session 2026-09-30, X-Plane 12.4.3, Phenom 300 at YBBN gate 24: BATC connected, showed the aircraft at the right gate, gave clearance, tuned COM1 in the X-Plane cockpit for ATIS, Clearance and Ground, and followed the aircraft while taxiing; X-Plane's own ATIS/ATC audio overlaps BATC's unless its radio volume is turned down): stands in for MSFS 2024 on `tcp:5112`, starts the `FlightSimulator2024` stub, and answers BATC from X-Plane 12's Web API (`127.0.0.1:8086`) through `mapping/simvars.yaml` and `mapping/events.yaml`. COM and transponder events from BATC are written to X-Plane. Aircraft data is held back until X-Plane reports a position. `--facilities` replays recorded airport data as in `fake`. Runbook: `docs/runbooks/phase1-xplane.md`.
- Airport data from X-Plane (Phase 2): flown with BATC on 2026-10-01, YBBN (Orbx) to YTWB with no MSFS data: gate, clearance, taxi route, SID, handoffs through Brisbane Centre, RNAV 11 approach into YTWB, no BATC errors. YSSY (Global Airports, never recorded from MSFS) gave the right gate, Sydney controller names, and a taxi route on real taxiways with a runway crossing. Automated weather (AWIS/AWOS/ASOS) goes out as MSFS type 12. `serve` answers BATC's airport requests from the X-Plane folder (found from X-Plane's install list, or `--xplane-root`): apt.dat in scenery_packs.ini order, CIFP procedures, fix positions and magnetic variation from nav data, and a generated taxi network where X-Plane has none (ADR-0003). `--facilities` replays recorded MSFS answers first. `XPConnect airport <ICAO>` writes what would be sent as JSON. The encoder reproduces MSFS 2024's recorded answers byte for byte; the generator is checked against MSFS's YBBN answer (runway and start positions, frequencies, parking within about 20 m). Conventions: `docs/protocol/facility-data.md`.
- `XPConnect xplane-check`: reads every mapped dataref from a running X-Plane and prints what BATC would get, flagging datarefs X-Plane does not have. Mappings marked `verify: true` still need this check.
- `XPConnect summarize`: builds the call inventory from a recording.
- Verified against an independent client (node-simconnect 4.2) over TCP, on both the SunRise and KittyHawk protocols.
- Recorded a real BATC session against MSFS 2024 (YBBN to YTWB, 2026-09-30). BATC is redirected by a `SimConnect.cfg` next to `simconnect_ws.exe` and another next to `BeyondATC.exe`. Findings: `docs/research/batc-call-inventory.md`.
- `ServerIdentity.Msfs2024` matches the recorded Open reply (SunRise 12.2.282174.999, SimConnect 12.2.0.0).
- Stand-in test passed (2026-09-30): with MSFS closed, BATC connects both SimConnect connections to `fake --identity msfs2024` and accepts the handshake, provided a process named `FlightSimulator2024.exe` is running (a do-nothing stub passes). With user-aircraft data and replayed facility data served, BATC loads YBBN and the flight plan, gives IFR clearance, tunes COM1 through us and issues a taxi route, all without MSFS (2026-09-30).
- Recordings sample high-rate streams (AI position writes, SimObjectData) to one per second per stream by default (`--throttle-ms`). A full-rate 30-minute flight was 2.9 GB.

## Not yet verified
- `serve` in flight (only ground work to taxi is verified). Wind (`verify: true`) not compared with the cockpit; design speeds and wingspan are fixed values.
- MSFS starting while XPConnect is running (step-aside), and whether other add-ons connected over the pipe (SayIntentions, NG Academy readers) misbehave when they get no answers.
- X-Plane traffic plugin (ADR-0004, `plugin/`, protocol `docs/protocol/plugin.md`): built on XPMP2, draws aircraft sent by XPConnect with CSL models, puts ground traffic on X-Plane's terrain and reports terrain height back. Compiles and its protocol tests pass on Linux; Windows build runs in GitHub Actions. XPConnect side: `PluginLink` (UDP), `xpconnect plugin install|remove|status`, double-click start offers to install it, status page shows it. `TrafficBridge` sends BATC's aircraft (not tugs) to the plugin 10 times a second, with type and airline from `mapping/traffic-models.yaml`, and answers BATC's ground-height polls with the plugin's terrain under that aircraft (nearest airport until the plugin has measured). Live in X-Plane since 2026-10-01 with Bluebell CSL models. Plugin 0.4.0 parks each CSL model on its own wheels, posed with the gear down from its .obj files (checked against Ben's 2,027 Bluebell models); per-type pitch and height in mapping/traffic-models.yaml are only a fallback for models it cannot fit. Plugin 0.3.1 blends between updates (smooth turns and climbs) and probes terrain less often; XPConnect sends unchanged parked aircraft every 2 s instead of 10 times a second; 0.3.2 stops those repeats sliding parked aircraft back and forth. 0.4.1 also levels the bogies of models that tilt them on World Traffic's gear dataref (Bluebell's virtual-airline repaints), and removes aircraft whose `del` UDP dropped; XPConnect repeats `del` and sends `clear` when it starts. A packet that fails to decode or handle is logged and no longer drops BATC's connection. Aircraft on the ground are drawn wings level (BATC writes a bank on the take-off roll). 0.4.2 patches XPMP2 (plugin/cmake/xpmp2-split-packages.patch) so CSL packages split over several folders load all their models: XPMP2 3.7.0 looked for each .obj in the first folder only, so about 750 Bluebell models (B744_QFA, B772_UAL...) were missing and BATC's aircraft fell back to virtual-airline repaints (YBBN 2026-10-03, 2,283 "could not be found" lines in Log.txt). 0.4.2 also finds each bogie's level from where its wheels end up, which levels the 747's wing-gear bogies (modelled already tilted, turning 30° to 73°). 0.4.3 draws BATC placing an aircraft (a move far faster than its speed) at once, instead of sliding it and overshooting back and forth.
- FSLTL import (ADR-0005, `src/XPConnect.Fsltl`, research `docs/research/fsltl-models.md`): `xpconnect fsltl import` converts the user's own FSLTL install into an X-Plane CSL package in `Custom Data/CSL/XPConnect-FSLTL` (glTF with Asobo's vertex packing to OBJ8 with LOD0 + a low LOD, gear/flap/slat/spoiler/reverser/wheel animations on XPMP2 datarefs, DDS textures capped at `--size`, BC7 re-encoded as DXT5). `serve` then sends BATC's exact livery key to the plugin. Dry run on Ben's FSLTL 1.5.0 (2026-10-03): 3,154 of 3,166 liveries, 198 models, 2,413 textures in 93 s at 1024 px; SU95 skipped (730k triangles), Asobo GA models not converted. First look in X-Plane (2026-10-04, YBBN): liveries, textures and faces right; SF34 drew a giant wheel (a scaled parent node was dropped; now pushed into the animated parts), E190 had its gear up (its gear animations are not in the model XML; animations missing from the XML are now judged by name), B738 mains sat slightly high because the plugin fitted wheels on both LODs (plugin 0.4.4 reads only the nearest LOD).
