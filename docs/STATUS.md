# Status

_Update this file in every PR that changes behaviour._

**Phase:** 2, airports from X-Plane's own data. Phase 1 (BATC answered from X-Plane, ground to climb) and Phase 0 passed.

## Works
- Traffic, XPConnect side (not drawn in X-Plane yet): `serve` answers EnumerateSimObjectsAndLiveries from `mapping/liveries.json` (the 5,497 models MSFS listed), creates BATC's AI objects (AssignedObjectId), keeps their state from SetDataOnSimObject and events, answers BATC's ground-height polls (nearest served airport's elevation, else the ground under the user), and lists the traffic on the status page. Replay-tested against the recorded MSFS session (`TrafficTests`). Live on Ben's PC 2026-10-01 at YBBN: BATC created 45 aircraft and 3 tugs and its AI traffic talked on Ground. `--no-traffic` turns it off.
- Everyday use (0.3.0): `scripts/publish.ps1` builds a self-contained Windows zip (`XPConnect.exe`, the `FlightSimulator2024.exe` stub, `mapping/`, `README.txt`, two .cmd switches). Double-clicking `XPConnect.exe` offers to point BATC at it and then serves; `xpconnect batc on|off|status` adds or removes the two `SimConnect.cfg` redirects (BATC folder from its uninstall entry or `C:\BeyondATC`; an existing cfg is backed up and restored). Outside a source checkout, recordings go to `%LOCALAPPDATA%\XPConnect\recordings`. Package smoke-tested on Ben's PC 2026-10-01.
- Status page: `serve` shows http://localhost:5577/ (X-Plane connection, both BATC connections, airports sent and where from, a one-line "what to start next"); double-click start opens it in the browser. `--status-port`, `--no-status`. Not yet seen on Ben's PC.
- SimConnect packet framing, function and message names, and decoding of the common ATC-client calls (`src/XPConnect.Protocol`).
- `XPConnect record`: pass-through proxy that records a real client/sim session to JSONL and writes a call inventory.
- `XPConnect fake`: answers the Open handshake as MSFS 2020 or 2024 and serves the user aircraft's SimVars from a fixed snapshot (SF50 parked at YBBN, live clock, COM set events applied). `--facilities <recording.jsonl>` replays the airport data MSFS sent in a pass-through recording. Everything else is recorded and left unanswered.
- `src/XPConnect.SimStub` builds `FlightSimulator2024.exe`, the do-nothing process BATC needs to see before it connects. A console process with no window passes.
- `XPConnect serve` (first real session 2026-09-30, X-Plane 12.4.3, Phenom 300 at YBBN gate 24: BATC connected, showed the aircraft at the right gate, gave clearance, tuned COM1 in the X-Plane cockpit for ATIS, Clearance and Ground, and followed the aircraft while taxiing; X-Plane's own ATIS/ATC audio overlaps BATC's unless its radio volume is turned down): stands in for MSFS 2024 on `tcp:5112`, starts the `FlightSimulator2024` stub, and answers BATC from X-Plane 12's Web API (`127.0.0.1:8086`) through `mapping/simvars.yaml` and `mapping/events.yaml`. COM and transponder events from BATC are written to X-Plane. Aircraft data is held back until X-Plane reports a position. `--facilities` replays recorded airport data as in `fake`. Runbook: `docs/runbooks/phase1-xplane.md`.
- Airport data from X-Plane (Phase 2): flown with BATC on 2026-10-01, YBBN (Orbx) to YTWB with no MSFS data: gate, clearance, taxi route, SID, handoffs through Brisbane Centre, RNAV 11 approach into YTWB, no BATC errors. YSSY (Global Airports, never recorded from MSFS) gave the right gate, Sydney controller names, and a taxi route on real taxiways with a runway crossing. Automated weather (AWIS/AWOS/ASOS) goes out as MSFS type 12. `serve` answers BATC's airport requests from the X-Plane folder (found from X-Plane's install list, or `--xplane-root`): apt.dat in scenery_packs.ini order, CIFP procedures, fix positions and magnetic variation from nav data, and a generated taxi network where X-Plane has none (ADR-0003). `--facilities` replays recorded MSFS answers first. `XPConnect airport <ICAO>` writes what would be sent as JSON. The encoder reproduces MSFS 2024's recorded answers byte for byte; the generator is checked against MSFS's YBBN answer (runway and start positions, frequencies, parking within about 20 m). Conventions: `docs/protocol/facility-data.md`.
- `XPConnect xplane-check`: reads every mapped dataref from a running X-Plane and prints what BATC would get, flagging datarefs X-Plane does not have. Mappings marked `verify: true` still need this check.
- `XPConnect summarize`: builds the call inventory from a recording.
- Verified against an independent client (node-simconnect 4.2) over TCP, on both the SunRise and KittyHawk protocols.
- Recorded a real BATC session against MSFS 2024 (YBBN to YTWB, 2026-09-30). BATC is redirected by a `SimConnect.cfg` next to `simconnect_ws.exe` and another next to `BeyondATC.exe`. Findings: `docs/research/batc-call-inventory.md`.
- `ServerIdentity.Msfs2024` matches the recorded Open reply (SunRise 12.2.282174.999, SimConnect 12.2.0.0).
- Stand-in test passed (2026-09-30): with MSFS closed, BATC connects both SimConnect connections to `fake --identity msfs2024` and accepts the handshake, provided a process named `FlightSimulator2024.exe` is running (a do-nothing stub passes). With user-aircraft data and replayed facility data served, BATC loads YBBN and the flight plan, gives IFR clearance, tunes COM1 through us and issues a taxi route, all without MSFS (2026-09-30).
- Recordings sample high-rate streams (AI position writes, SimObjectData) to one per second per stream by default (`--throttle-ms`). A full-rate 30-minute flight was 2.9 GB.

## Not yet verified
- `serve` in flight (only ground work to taxi is verified). Wind (`verify: true`) not compared with the cockpit; design speeds and wingspan are fixed values.
- X-Plane traffic plugin (ADR-0004, `plugin/`, protocol `docs/protocol/plugin.md`): built on XPMP2, draws aircraft sent by XPConnect with CSL models, puts ground traffic on X-Plane's terrain and reports terrain height back. Compiles and its protocol tests pass on Linux; Windows build runs in GitHub Actions. XPConnect side: `PluginLink` (UDP), `xpconnect plugin install|remove|status`, double-click start offers to install it, status page shows it. `TrafficBridge` sends BATC's aircraft (not tugs) to the plugin 10 times a second, with type and airline from `mapping/traffic-models.yaml`, and answers BATC's ground-height polls with the plugin's terrain under that aircraft (nearest airport until the plugin has measured). Not yet loaded in X-Plane; needs a CSL package such as Bluebell.
- BATC's `simconnect_ws.exe` connecting to our named pipe on Windows (message-mode pipe, security).
- BATC's behaviour in flight without MSFS (reconnects, any checks later in a flight). Ground work up to taxi is verified with the stand-in.
- What triggers the EXTERNAL_SYSTEM_SET/TOGGLE events BATC receives (probably key bindings inside MSFS).

- Phase 2 airport data with BATC: taxi routes on the generated network (YTWB has no tower, so BATC gives no taxi route there; needs a towered airport without X-Plane taxiways). BATC vectored heavily before the YTWB approach although the approach data matches MSFS; compare with an MSFS flight. Unsure: MSFS's MAGVAR convention (YTWB and YBAF say 349 for 11 E, YBBN says 11; we send 349), helipads (not sent).
